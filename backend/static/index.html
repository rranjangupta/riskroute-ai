How RiskRoute works

Tier 1 · every payment · milliseconds

Static bank rules (new payee, new device, contact change, high value) + the customer's stored behaviour profile (one read, updated incrementally on every released payment). No mandatory rule and normal behaviour → auto-clear, no AI call.

→
Tier 2 · flagged payments · async

Flagged payments are queued on Pub/Sub. A Gemini agent on Vertex AI calls tools for the transaction, payee, account activity and profile, then writes a structured investigation. A citation check removes claims citing records it never fetched.

→
Route

Auto-clear routine
Customer verification self-service, no staff
Analyst review strong takeover/scam signals only

Event-driven architecture on Google Cloud

Payment events→Pub/Sub payments-in→Cloud Run · Tier 1→Pub/Sub flagged-payments→Cloud Run · Gemini worker→Firestore · cases, profiles, audit
  • Idempotent: duplicate Pub/Sub deliveries are ignored; investigations are claimed with a Firestore transaction.
  • Back-pressure: limited parallel Gemini calls per instance; quota errors are retried by Pub/Sub with backoff, then fall back to rules-only routing.
  • Cost guard: daily caps on AI investigations and feed volume.

Guardrails

  • Mandatory rules set a minimum route. The AI can escalate but never go below it.
  • If the registered mobile changed recently, a customer confirmation is not trusted and goes to an analyst.
  • The AI recommends; it never moves money. Every action is written to the audit log. All data is synthetic.
